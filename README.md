## Project Initiator — Skill Chain

The Project Initiator is a Claude Code toolchain for fiftyfive-tech consultants. It converts raw client engagement docs into structured project-starting artifacts through a guided conversation chain.

**Full chain:** START → DISCOVERY → MVP_SYNTHESIZER → ARCH_PROPOSER → DOC_GENERATOR → BACKLOG_GENERATOR → ESTIMATOR

Each skill is run manually from the engagement folder. Every skill writes its output file and updates `session_state.md` on completion.

---

### Folder convention

```
~/fiftyfive-engagements/
  active/
    supplysync/          ← engagement folder (one per client)
      input/             ← raw docs go here (PDF, text, markdown)
      project.md         ← created by START
      session_state.md   ← updated by each skill on completion
      discovery.md       ← generated by DISCOVERY
      mvp-scope.md       ← generated by MVP_SYNTHESIZER
      arch.md            ← generated by ARCH_PROPOSER
      docs/              ← generated by DOC_GENERATOR
      backlog.md         ← generated by BACKLOG_GENERATOR
      estimates.md       ← generated by ESTIMATOR
  blocked/
  completed/
  archived/
```

### START (V1.3)

**File:** `skills/project-initiator/START.md`

**How to run:** From `~/fiftyfive-engagements/` (parent directory). Say `run START`.

**What it does:**
- Scans all engagement folders across `active/`, `blocked/`, `completed/`, `archived/` buckets
- Shows a numbered registry of all engagements with their current stage and last session date
- For a new engagement: asks client name, engagement name, project type — then creates the folder structure with confirmation
- For an existing engagement: shows the current stage, open items from the last session, and which skill to run next
- Supports status transitions between buckets (active → blocked → completed → archived → reactivate)

**Generates:**
- `~/fiftyfive-engagements/active/<slug>/` folder structure
- `project.md` — engagement metadata (client, type, stage, status, dates)
- `session_state.md` — current stage, next step, open items

**Does NOT do:** run any downstream skill automatically — it tells you which to run next.

### DISCOVERY (V1.0)

**File:** `skills/project-initiator/DISCOVERY.md`

**How to run:** Open Claude Code in the `<client-name>/` folder (not `input/`). Say `run DISCOVERY`.

**Requires:** `input/` subfolder with at least one readable doc (`.pdf`, `.txt`, `.md`)

**What it does:**
- Reads all input docs and extracts: project type, users, core problem, features, tech, timeline, constraints
- Assigns confidence levels (HIGH / MED / LOW) to each extracted item
- Surfaces conflicts (same topic stated differently across docs) and resolves them one by one
- Asks critical gap questions — things MVP_SYNTHESIZER cannot proceed without
- Lets you defer any question to Open Questions
- Shows the full draft for review before writing

**Generates:** `discovery.md` — structured artifact with sections: Project Context, Users, Core Problem, Features Mentioned, Constraints, Open Questions, Confidence Notes, Source Docs. Also updates `session_state.md`.

**Does NOT do:** choose architecture, define MVP scope, select tech stack, or create tickets.

### MVP_SYNTHESIZER (V1.1)

**File:** `skills/project-initiator/MVP_SYNTHESIZER.md`

**How to run:** Open Claude Code in the `<client-name>/` folder. Say `run MVP_SYNTHESIZER`.

**Requires:** `discovery.md` (produced by DISCOVERY)

**What it does:**
- Runs a Readiness Gate on `discovery.md` — checks for core problem, users, ≥2 features, timeline, no unresolved conflicts. BLOCKs are resolved inline before proceeding.
- Presents 3 MVP framing options: Time-boxed / Risk-first / Value-first — consultant picks one
- Goes through every feature from DISCOVERY and assigns it IN / OUT / DEFERRED based on the chosen framing
- Extracts 2–4 key end-to-end user journeys the MVP must support
- Asks for success metrics (or defers to Open Questions)
- Shows the full draft for review before writing

**Generates:** `mvp-scope.md` — structured artifact with sections: Problem Restatement, Users, MVP Framing, Scope In/Out tables, Key User Journeys, Success Metrics, Constraints, Assumptions, Open Questions, Effort Signals (placeholder), Confidence Notes. Also updates `session_state.md`.

**Does NOT do:** choose architecture or tech stack. Effort signals are deferred to ARCH_PROPOSER.

### ARCH_PROPOSER (V1.3)

**File:** `skills/project-initiator/ARCH_PROPOSER.md`

**How to run:** Open Claude Code in the `<client-name>/` folder. Say `run ARCH_PROPOSER`.

**Requires:** `mvp-scope.md` (produced by MVP_SYNTHESIZER)

**What it does:**
- Runs a Readiness Gate on `mvp-scope.md` — checks scope, users, tech constraints, timeline, budget, no unresolved conflicts
- Shows confirmed tech from mvp-scope.md as locked, then walks through unconfirmed layers (backend, database, infra, mobile) one at a time with 2–3 options each from fiftyfive-tech's preferred stack list
- Derives components per feature from the confirmed stack, presents as a single block for review
- Identifies integration points with risk ratings and open questions
- Asks for team composition, then maps components to a sprint plan
- Derives S/M/L/XL effort signals per feature from component count + integration risk
- Marks tentative decisions as `[STRAWMAN]` — these become blocking pre-condition tickets in BACKLOG_GENERATOR
- Produces a plain-language Client Summary (no jargon) as the final section

**Generates:** `arch.md` — structured artifact with sections: Client Summary, Tech Stack, Components, Data Model Hints, Integration Points, Build Order, Sprint Mapping, Effort Signals, Open Questions, STRAWMAN Summary, Confidence Notes. Also updates `session_state.md`.

**Does NOT do:** create Odoo tickets (that is BACKLOG_GENERATOR's job).

### DOC_GENERATOR (V1.3.5)

**File:** `skills/project-initiator/DOC_GENERATOR.md`

**How to run:** Open Claude Code in the `<client-name>/` folder. Say `run DOC_GENERATOR`.

**Requires:** `discovery.md`, `mvp-scope.md`, `arch.md` all present

**What it does:**
- Runs a Sync Check — cross-validates all three input files for consistency. DRIFT items block the menu until resolved or deferred. WARNs pass through and are flagged in affected docs.
- Presents a menu of deliverable documents to generate (not all are required)
- Generates each selected doc with Mermaid diagrams, gets consultant approval per doc
- Saves each approved doc to the `docs/` subfolder

**Generates** (saved to `<engagement-folder>/docs/`):
- **Project Proposal / SOW** — client-facing scope and commercial terms
- **Technical Architecture Doc** — developer-facing with stack, components, diagrams
- **Sprint Plan** — sprint-by-sprint work breakdown for internal use
- **Developer Handoff Doc** — component specs, data model, integration notes, open questions
- **Scope Agreement** — sign-off document for client

**Does NOT do:** ask new questions — all data comes from upstream artifacts.

### BACKLOG_GENERATOR (V1.4.1) — includes Odoo MCP ticket creation

**File:** `skills/project-initiator/BACKLOG_GENERATOR.md`

**How to run:** Open Claude Code in the `<client-name>/` folder. Say `run BACKLOG_GENERATOR`.

**Requires:** `arch.md` with sections: `## Sprint Mapping`, `## Build Order`, `## Components`, `## Tech Stack`

**What it does — full flow:**

1. **Project Setup** — asks for Odoo project name (defaults to engagement name) and stages (defaults to Backlog / To Do / In Progress / Bug / Done). Calls `list_active_projects` to check for an existing project before creating.

2. **Sprint Tags** — creates one Odoo tag per sprint label (e.g. "Sprint 1-2", "Sprint 3-4") via `create_tag`. Every ticket gets its sprint tag.

3. **Team Mapping** — shows team roles extracted from arch.md Sprint Mapping, asks for Odoo user ID per role. Validates each ID against `list_metadata`. Invalid IDs are warned inline — consultant can re-enter or leave unassigned.

4. **Duplicate Check** — calls `list_tickets` on the project and compares generated ticket titles (case-insensitive exact match) against existing titles. Duplicate matches are surfaced with options: skip, cancel, or create anyway.

5. **Ticket generation** — builds a full ticket hierarchy from arch.md:
   - One **parent ticket** per Build Order item — title format: `[Sprint N] <item name>`
   - One **subtask** per component listed under that Build Order item
   - Shared components get a subtask only in the ticket where they are first built; later tickets reference them as a note only
   - **STRAWMAN tickets** for each item in `## STRAWMAN Summary` — placed in Backlog stage, high priority, deadline = Sprint 1 start date
   - Backend tickets include: Scope, API Endpoints (or Interfaces for connectors/jobs), Key Business Rules, Acceptance Criteria, Edge Cases, Open Questions
   - Frontend tickets include: Scope, Screens & Components, Key Business Rules, Acceptance Criteria, Edge Cases, Open Questions

6. **Preview + Approval Gate** — shows the full ticket set in a table (parent tickets with subtasks, STRAWMAN tickets) before any creation. Consultant can edit or approve. `backlog.md` is written on approval.

7. **Next Steps Gate** — after `backlog.md` is written, asks:
   - `[A] Create tickets in Odoo now` → proceeds to Bulk Creation
   - `[B] Run ESTIMATOR first` → stops, tells you to run ESTIMATOR (which has its own Odoo gate)
   - `[C] Skip — keep backlog.md as draft` → saves DRAFT, can push later by re-running BACKLOG_GENERATOR

8. **Bulk Creation (Odoo MCP calls):**
   - `bulk_create_tickets` for all parent tickets with full descriptions, stage IDs, assignee IDs, tag IDs, priority, deadline
   - `add_subtasks` per parent ticket for its component subtasks
   - `bulk_create_tickets` (separate call) for STRAWMAN tickets in Backlog stage

**Generates:**
- `backlog.md` — full backlog with project config, team mapping, sprint tags, all ticket descriptions and metadata (Status: DRAFT → updated to CREATED after Odoo push)
- Odoo project with stages (if new)
- Sprint tags in Odoo
- Parent tickets + subtasks in Odoo
- STRAWMAN pre-condition tickets in Odoo

**Odoo MCP tools used:** `list_active_projects`, `create_project`, `create_tag`, `list_metadata`, `list_tickets`, `bulk_create_tickets`, `add_subtasks`

**Push Mode** — if `backlog.md` already exists with `Status: DRAFT`, re-running BACKLOG_GENERATOR offers to push the existing draft to Odoo without regenerating it.

### ESTIMATOR (V1.5)

**File:** `skills/project-initiator/ESTIMATOR.md`

**How to run:** Open Claude Code in the `<client-name>/` folder. Say `run ESTIMATOR`.

**Requires:** `arch.md` (with `## Effort Signals`, `## Sprint Mapping`, `## Build Order`) and `backlog.md` (produced by BACKLOG_GENERATOR)

**What it does:**
- Detects the project start date from arch.md; asks you to confirm or override it (date shifts preserve sprint durations)
- Asks for estimate style (fixed hours or range), working hours/day, and whether to include cost estimates
- For cost: supports a single blended day rate or per-role rates
- Converts S/M/L/XL effort signals to hours and days using your chosen values
- Maps each Build Order item to its sprint dates from backlog.md
- Shows the full estimate table for review; you can adjust any row before writing
- After writing estimates.md, asks whether to create Odoo tickets now (delegates to BACKLOG_GENERATOR Bulk Creation flow)

**Generates:** `estimates.md` — flat Markdown tables suitable for export to Excel/PDF/Word, with:
- **Summary block** — total effort, timeline, team size, sprint count, cost
- **Section 1 (Client Summary)** — grouped by sprint, one row per Build Order item
- **Section 2 (Detailed Breakdown)** — one row per parent ticket with start/end dates and assignee
- **Section 3 (Assumptions)** — hour-to-size mapping, working hours/day, cost rates, exclusions

**Does NOT do:** modify `arch.md`, `backlog.md`, or any upstream file. S/M/L/XL labels never appear in `estimates.md` — always converted to hours/days.

## Creating Odoo Tickets via BACKLOG_GENERATOR

The full Odoo creation flow — from zero to a populated Odoo board — runs as follows:

### Prerequisites
- `arch.md` present in the engagement folder (produced by ARCH_PROPOSER)
- Odoo MCP server running (`odoo-mcp/`) and connected to Claude Code
- Odoo user IDs for your team members (ask Odoo admin or use `list_metadata` to look up)

### Step-by-step

1. Open Claude Code in `~/fiftyfive-engagements/<client-name>/`
2. Say: `run BACKLOG_GENERATOR`
3. **Project name** — accept the default (engagement name) or type a new one
4. **Stages** — accept defaults (Backlog / To Do / In Progress / Bug / Done) or provide custom
5. **Team mapping** — enter the Odoo user ID for each role from arch.md Sprint Mapping. Type `skip` for any role to leave it unassigned.
6. **Preview** — review the full ticket table. Edit any row if needed. Type `yes` or `[A]` to approve.
7. **Next Steps Gate** — type `[A]` to create tickets in Odoo now, or `[B]` to run ESTIMATOR first.
8. **Odoo creation** — BACKLOG_GENERATOR calls `bulk_create_tickets`, `add_subtasks`, and a second `bulk_create_tickets` for STRAWMAN tickets. Progress is shown inline.
9. Done — `backlog.md` is updated to `Status: CREATED` and `session_state.md` is updated.

### What appears in Odoo after creation

| What | Where in Odoo | Details |
|---|---|---|
| New project | Projects list | Name from engagement, custom stages |
| Sprint tags | Tags | One tag per sprint label (e.g. "Sprint 1-2") |
| Parent tickets | Project board | One per Build Order item, tagged with type + sprint |
| Subtasks | Under each parent | One per component; shared components not duplicated |
| STRAWMAN tickets | Backlog stage | One per tentative decision; high priority; unassigned |

### Re-running / push mode

If you ran BACKLOG_GENERATOR before and chose `[C] Skip` (kept backlog.md as DRAFT), you can push it to Odoo later:
1. Re-run BACKLOG_GENERATOR from the same folder
2. It detects `backlog.md` with `Status: DRAFT` and offers `[A] Push backlog.md to Odoo now`
3. Select `[A]` — it runs the full creation flow using the existing backlog.md
